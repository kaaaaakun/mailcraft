# 作業フロー(オーナー合意事項)

オーナーの方針: **PR が揃ったら、サブエージェント同士が互いの PR をレビューし、問題がなければマージする。今後はこの体制で進める。**
本書はその運用ルールの正本。

## 全体フロー

```
依頼
 └─> 分解 (並列にできるか? ファイル所有範囲は分かれているか?)
       └─> 各サブエージェントが別 worktree で branch 作成 + PR
             └─> CI (typecheck / test / build / build:lib)
                   └─> 相互レビュー (作者以外が現在の head SHA に対してコメント)
                         │
                         ├─ blocker / major あり
                         │     └─> 作者が修正 push ─> CI ─> 再レビュー (最初に戻る)
                         │         (2 往復で解決しない / 意見不一致 ─> オーナーへ)
                         │
                         ├─ オーナー確認が必要な変更を含む ─> オーナーの判断を待つ (自動マージしない)
                         │
                         └─ 問題なし
                               └─> squash merge (オーケストレーター)
                                     └─> main の CI / Pages デプロイ確認
                                           └─> オーナーへ報告
```

## 1. 作業単位

- 作業はオーナーの指示のもと、サブエージェントが行う。
- **1 PR = 1 目的。**
- ブランチ名: `feat/…`(機能)、`fix/…`(不具合)、`docs/…`(ドキュメント)。保守・リファクタ・テスト用に `chore/…` `refactor/…` `test/…` も可。
- 必ず PR 経由で main に入れる。**main へ直接 push しない。**

## 2. 並列化

- 並列にできる作業は並列で行う。
- 衝突を避けるため、エージェントごとに触るファイルの範囲を分ける。
- 同じファイルを大きく触る作業(例: UI 全面改修)は、先行 PR のマージ後に着手する。
- 着手後に同じファイルで衝突した場合の手順は「5. マージ条件」の「先行 PR がマージされた後の更新」に従う。
- 各エージェントは別の worktree で作業する。

## 3. PR の要件

- 本文に **目的 / 変更点 / 検証結果 / 互換性 / 既知の制限** を書く。
- 次がローカルで通ること: `npm run typecheck` / `npm test` / `npm run build` / `npm run build:lib`。
- CI が緑(`.github/workflows/ci.yml` は上記 4 つを `npm ci` の後に実行する)。
- UI 変更は実ブラウザで確認し、スクリーンショットを載せる(ドキュメントのみ・UI に影響しない PR は不要)。
- README / `docs/ARCHITECTURE.md` など関連ドキュメントを更新する。
- コミットメッセージ末尾に `Co-Authored-By: …` を付ける。
- PR 本文末尾に生成表記(`🤖 Generated with [Claude Code](https://claude.com/claude-code)`)を付ける。
- `@メンション` を書かない(通知が飛ぶため)。

## 4. 相互レビュー

PR が揃ったら、各 PR を **その PR の作者ではない** サブエージェントが 1 回以上レビューする(作者同士のローテーション可)。
オーケストレーター自身が作った PR も、サブエージェントのレビューが必須。

### レビューコメントの形式

PR にコメントとして残す(`gh pr review --comment` / `gh pr comment`)。全員が同一 GitHub アカウントのため Approve は使えず、コメントで判定を示す。
**コメントの冒頭**に次の 2 行を書く:

```
Reviewed SHA: <レビュー対象の head commit SHA>
Verdict: APPROVE相当 / 要修正 (blocker・major の件数)
```

続けて指摘を blocker / major / minor / nit に分類して列挙する。

- レビューは **レビュー時点の head SHA** に対してのみ有効。**レビュー後に push があれば旧レビューは無効**で、再レビュー(作者以外)が必要。
- オーケストレーターはマージ前にレビューコメントを読んで判断する。**レビュアーの blocker / major をオーケストレーター単独で覆してはならない。**

### チェックリスト

- [ ] 正しさ / 回帰
- [ ] セキュリティ(XSS・入力検証・URL の扱い)
- [ ] テストの十分さ
- [ ] 後方互換(公開 API・JSON スキーマ)
- [ ] 他の PR との衝突
- [ ] i18n(en / ja のパリティ)・a11y
- [ ] ドキュメントの正確さ(実装と食い違う主張がないか)
- [ ] ライセンス / 公開設定に触れていないか

### 指摘の分類

迷ったら **重い方の区分** にする。

| 区分 | 定義 | マージ |
| --- | --- | --- |
| blocker | 動作しない・既存機能の回帰・データ破損・**深刻なセキュリティ問題**・オーナー決定やこの文書のルール違反 | 不可 |
| major | 公開 API / JSON スキーマの互換性破壊の疑い、主要な振る舞いのテスト欠如、実装と食い違うドキュメント、他 PR との衝突 | 不可 |
| minor | 直した方がよいが、動作や安全性に影響しない | 可(対応推奨) |
| nit | 好みレベル | 可 |

- 深刻なセキュリティ指摘は blocker とし、オーナーが明示的に許可しない限りマージしない。
- blocker / major が未解決ならマージしない。作者が修正 push し、再レビューを受ける。

### 意見不一致・エスカレーション

- 作者が指摘に同意しない場合は PR 上で根拠を書く。レビュアーが取り下げない限り、指摘は有効のまま。
- 意見が割れたまま、または 2 往復のレビューで解決しない場合は **オーナーへエスカレーション** する。オーケストレーターが単独で決着させてはならない。

## 5. マージ条件(すべて満たす)

1. CI 緑。
2. **作者以外のエージェントによるレビューコメントが、現在の head SHA に対して 1 件以上** あり、未解決の blocker / major がない。
3. コンフリクトなし。
4. 下記「6. オーナーの事前確認が必要なもの」を含まない。

- 方法: squash merge(`gh pr merge --squash --delete-branch`)。マージした PR 自身のブランチの削除は定常操作として許可する。
- 順序: 依存の少ない順。コア → エディタ → 見た目。
- **マージの実行はオーケストレーター(メインの Claude)が行う。** マージ後に main の CI と Pages デプロイ(`pages.yml`)が緑か確認し、結果をオーナーへ報告する。

### 先行 PR がマージされた後の更新

先行 PR のマージで main が進み、同じファイルで衝突する/しそうな場合:

1. 後続 PR のブランチに **`origin/main` を merge する**(rebase しない。force push しない)。squash merge なので main の履歴は汚れない。
2. 衝突を解消して通常の push をする。
3. CI を再実行し、緑を確認する。
4. 衝突解消が自明でない場合は再レビューを受ける(push 後は旧レビューが無効になる点は変わらない)。
5. その後マージする。

force push は、自分の PR ブランチであっても **オーナー確認が必要**(6 参照)。

### CI が赤い / 不安定な場合

- 失敗の原因を確認する。変更と明らかに無関係な場合に限り re-run してよい。
- CI のスキップ、失敗の無視、管理者権限でのマージ、テストの無効化・削除による回避は **禁止**。
- 失敗が繰り返される場合はオーナーへ報告する。

### ブランチ保護について

現時点で main にブランチ保護は設定されていない。そのため **本書のルールが唯一の安全装置**になる。
「PR 必須・CI 必須」の保護設定をオーナーが検討することを推奨する(設定変更はエージェントが行わない)。

## 6. オーナーの事前確認が必要なもの(自動マージしない)

- リポジトリの公開範囲の変更
- Pages 設定の変更
- npm 公開
- ライセンスの変更
- 履歴の書き換え / force push(自分の PR ブランチへのものを含む)
- ブランチ・リポジトリ・Issue の削除(ただし、マージした PR 自身のブランチを `gh pr merge --delete-branch` で削除することは除く)
- 外部サービスへの課金や権限付与
- GitHub Actions の権限・シークレット・設定の変更、`.github/workflows/` の `permissions:` の変更
- セキュリティ上重大な指摘が未解決のもの

## 7. 設計判断・デザイン方針

GitHub Issue(label: `design` / `discussion`)で議論し、オーナーの決定を待つ。決定済み事項は各 Issue のコメントに従う。

## 8. 環境メモ

- この環境では SSH の git が固まる。HTTPS で push する:
  `git -c "credential.helper=!gh auth git-credential" push https://github.com/kaaaaakun/mailcraft.git HEAD:refs/heads/<branch>`
- `pkill -f` はシェルごと巻き込むことがある。ポート指定で `fuser -k <port>/tcp` を使う。
- プレビュー(`vite preview`)のポートはエージェントごとに分ける。
- 実ブラウザ検証は `playwright-core`(Chromium)。`package.json` には含まれないので、必要なときだけ `npm i --no-save playwright-core` で入れる。
  `tests/e2e/*.mjs` は Chromium の `executablePath` をスクリプト内で指定している(例: `~/.cache/ms-playwright/…`)ため、環境に合わせて書き換える。使い方は各スクリプト冒頭のコメントを参照。
